# Variants

## What Variants Are

**Variants** are optional alternative implementations of the same logic. Each entry is a self-contained code snippet showing a different valid approach. All variants are structural equals.

No variant is "better." No variant is "preferred." They coexist.

## Structure

```json
{
  "variants": [
    "evens = list(filter(lambda x: x % 2 == 0, range(20)))",
    "evens = []\nfor x in range(20):\n    if x % 2 == 0:\n        evens.append(x)"
  ]
}
```

- Each entry is a complete, self-contained code snippet.
- **null**: No variants. The snippet works identically without them.
- Order is preserved but carries no meaning.

## Ethical Boundaries

### No Ranking

Variants are peers. The authoring format provides no mechanism for:
- Marking a variant as "preferred" or "recommended"
- Ordering variants by quality
- Labeling variants as "best practice" or "anti-pattern"
- Attaching difficulty or skill-level metadata to individual variants

This is enforced by reflection tests: `ImportedSnippets_HaveNoPedagogyMetadata` verifies no `PreferredVariant`, `Rank`, or similar properties exist on `Snippet`.

### No Attribution

Variants carry no author metadata. A variant from a shared pack is indistinguishable from a locally-authored variant. This is by design.

### No Judgment

The display uses the header "Other approaches" (not "Better approaches," "Alternative solutions," or "Try these instead"). The `=` prefix means equivalence.

## Authoring Guide

### Each Variant Should Be:

1. **Complete**: Runnable on its own (not a fragment).
2. **Different**: A genuinely different approach (not a minor syntax variation).
3. **Self-contained**: No dependency on the main snippet's variable names.

### Good Variants

A list comprehension snippet might have variants showing:
- A `filter()` approach
- An explicit `for` loop
- A generator expression

Each solves the same problem differently. None is "better."

### What Not to Include

- Broken or intentionally bad code
- Trivial whitespace differences
- The same logic with different variable names
- Code that only works in specific frameworks

## Display Behavior

1. Variants appear on the completion card, behind the Details toggle.
2. Header: "Other approaches" (non-hierarchical).
3. Each variant displays in a monospace code card with subtle background.
4. `=` prefix (equivalence symbol).
5. The `ShowVariants` toggle in the sidebar hides the entire section.
6. The app never tracks which variants a user reads.

## Why Variants Coexist as Equals

Teaching through exposure means showing multiple valid paths without steering. A developer who sees three ways to filter a list learns that the problem space has breadth. They don't need someone to tell them which is "best" — they can form their own judgment through practice.

This is pedagogy through structure, not instruction.

## Engine Isolation

Variants are display-only. They never affect:
- Snippet selection or weighting
- Difficulty calculation or adjustment
- Rating computation
- XP calculation
- Any engine behavior whatsoever

This is enforced by reflection tests in `ProfileInvariantTests.cs`.
