Witness is structured as a layered Python library with a CLI frontend. Each layer has a single responsibility and clear boundaries.

## Project layout

```
witness/
├── src/witness/           # Core library
│   ├── canon.py           # Canonical JSON serialization
│   ├── crypto.py          # Ed25519 signing and verification
│   ├── models.py          # Data models (events, verification results)
│   ├── storage.py         # SQLite append-only store
│   ├── timeline.py        # Flag analysis across events
│   ├── testify.py         # Testimony generation
│   └── cli.py             # Command-line interface
├── schemas/               # JSON schemas
├── tests/                 # Test suite (128 tests)
│   └── fixtures/golden/   # Authoritative golden fixtures
├── tools/                 # Verification utilities
└── docs/                  # Documentation and ADRs
```

## Core modules

### canon.py -- Canonical JSON

Deterministic serialization that produces identical bytes for identical data. This is the foundation of all cryptographic operations. The rules (sorted keys, no whitespace, UTF-8, no scientific notation) are locked and cannot change without a schema version bump.

### crypto.py -- Ed25519 operations

Signing and verification using the `cryptography` library. Public keys and signatures are base64-encoded. Key IDs are derived as `sha256(public_key_bytes)` in lowercase hex.

### models.py -- Data models

Typed dataclasses for all core structures: `WitnessEvent`, `VerifyResult`, `VerifyStatus`, `Artifact`, `Actor`, `Signing`, `Integrity`, `Links`, and `Rotation`. These define the shape of events, verification outcomes, and key rotation context used throughout the codebase.

### storage.py -- Append-only SQLite store

The event journal is a SQLite database where events are only ever inserted, never updated or deleted. This enforces the append-only invariant at the storage layer.

### timeline.py -- Flag analysis

Walks the full event history to detect anomalies: broken continuity, temporal anomalies after key rotation, key reactivation, and unexpected actor types on rotation events. Flags are informational and never block verification.

### testify.py -- Testimony generation

Bundles events into portable reports (Markdown, JSON, or plain text). Supports deterministic output via `--generated-at` and artifact emission with integrity manifests.

### cli.py -- Command-line interface

The public API surface. Commands: `init`, `record`, `inspect`, `verify`, `export`, `rotate-key`, and `testify`. All other modules are internal.

## Design decisions

### Separation of crypto and timeline

Cryptographic verification is per-event and self-contained. Timeline analysis requires the full event sequence. These are deliberately separate concerns:

- Crypto failure means the event was tampered with or corrupted (exit code 3)
- Timeline flags mean something unusual happened but crypto is valid (exit code 2)

A timeline issue never invalidates cryptographic proof.

### No key registry

There is no separate key table. Key state is inferred entirely from rotation events in the journal. This keeps the trust model simple: the journal is the single source of truth.

### Golden fixtures as spec

The golden fixtures under `tests/fixtures/golden/` are the authoritative specification. Implementation correctness means matching these fixtures exactly. They are generated by `tools/gen_golden.py` and verified by `tools/verify_golden.py`.

Golden fixtures are never hand-edited. Any change to canonicalization, digest scope, or signing rules requires regenerating them.

### Contract documents

| Document | Role |
|----------|------|
| CONTRACT.md | Defines what is law vs. example |
| IMPLEMENTATION_NOTES.md | Locked invariants (do not change without schema bump) |
| VERIFICATION.md | Crypto rules and worked examples for third-party implementors |

## Phase 2 tracks

Witness development is organized into independently shippable tracks. Phase 1 guarantees are never modified by Phase 2 work.

| Track | Status | Scope |
|-------|--------|-------|
| 2A: Testimony as Artifact | Shipped | Deterministic rendering, stable JSON schema, artifact emission |
| 2B: Pipeline Composition | Paused | Stage-based testimony generation (internally proven, intentionally unshipped) |
| 2C: Provenance Interop | Not started | PROV-style export, MCP envelope compatibility |
| 2D: Multi-Actor | Not started | Multiple actors, claim lifecycle |
| 2E: Time Anchoring | Not started | External notarization (optional, late phase) |

### What Phase 2 will not do

Out of scope for all tracks: identity proof, trust scoring, policy enforcement, cloud sync, and AI judgment of intent. Witness remains neutral.
